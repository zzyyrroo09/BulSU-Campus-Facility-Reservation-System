Executive System Summary & Compliance Report
1. Architecture & Scope: Built as a monolithic Django application complying strictly with the absolute prohibition of django.contrib.admin, admin.site.urls, and automated admin packages. Exactly two roles exist: BASIC USER and ADMIN. The workload satisfies the 75% custom admin side (/manage/) and 25% user portal (/portal/) distribution.
2. Anti-Conflict & Concurrency Engine: Time intervals follow half-open logic: $[start, end)$. Two intervals collide if and only if $start_A < end_B$ and $end_A > start_B$. Adjacent intervals meeting at the same endpoint ($end_A = start_B$) do not conflict. Competing approvals for the same venue/slot execute within transaction.atomic() utilizing select_for_update() row locks; the first commits while the second is blocked and rejected.
3. Lifecycle & Operations: Strict finite state machine transitions: $\text{Pending} \rightarrow \text{Approved} \rightarrow \text{Checked In} \rightarrow \text{Completed}$. Physical check-in is mandatory before event completion. Approved rescheduling retains complete timestamp history in ReservationChange. Official reservation slips with signature blocks are print-ready.
4. Data Privacy Safeguards (RA 10173): Basic user calendar views scrub private organizer names, student numbers, and event titles, displaying occupied blocks solely as "Occupied / Reserved Slot". Custom middleware (AccountActiveCheckMiddleware) invalidates active sessions immediately upon account deactivation while preserving past transactions for institutional auditability.
